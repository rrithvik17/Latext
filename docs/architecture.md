# Latext Future Architecture (Phase 2 & Beyond)

This document details the planned evolution of Latext from the Phase 1 MVP to a production-ready, horizontally scalable, scheduled message delivery platform.

## High-Level Architecture Diagram

                    │    Frontend     │

## Architectural Components

### 1. API Gateway & Routing
In future phases, an **API Gateway** (such as Kong or Traefik) will act as the single entry point. It will route traffic to domain-specific microservices and terminate SSL/TLS.

### 2. Microservices
We will decouple the monolithic backend into independent microservices:
- **Auth Service**: Manages users, credentials, and token issuance.
- **Messaging Service**: Handles instant 1-to-1 and group chats, WebSocket connection routing, and delivery status updates.
- **Scheduling Service**: Exposes APIs for scheduling, updating, and cancelling deferred/recurring messages.

### 3. Messaging Queue (Kafka/RabbitMQ)
For reliable asynchronous delivery:
- Scheduled message metadata is stored in PostgreSQL.
- A scheduler daemon publishes messages that are due for delivery onto a highly durable, partitioned queue (like **Apache Kafka** or **RabbitMQ**).
- Kafka enables horizontal scaling of consumers and guarantees message ordering per conversation.

### 4. Distributed Scheduler (Celery / Custom Workers)
- We will introduce **Celery** or custom Python worker daemons to consume from the message queue and handle delivery.
- Workers will process tasks such as pushing to WebSocket gateways, triggering push notifications, or writing to external SMS/Email APIs.

## Reliability and Scaling Patterns

### 1. Idempotent Processing
To ensure messages are not delivered multiple times (due to network retries), every message will carry an idempotency key (generated by the client).
- Workers will verify if the idempotency key has already been successfully processed (caching keys in Redis for high-speed checks).

### 2. Retries and Dead-Letter Queues (DLQ)
- If a delivery attempt fails (e.g., target client offline, external API down), the message will be retried with exponential backoff.
- After a maximum number of attempts, the message moves to a **Dead-Letter Queue (DLQ)** for manual inspection or alert-based resolution.

### 3. Distributed Locking (Redis Redlock)
To prevent duplicate scheduling runs or race conditions during concurrent worker polling, we will utilize **Redis** for distributed locking (using the Redlock algorithm).

### 4. WebSocket Scale-Out (Redis Pub/Sub)
To support horizontal scaling of WebSocket servers, we will replace the in-memory WebSocket manager with a **Redis Pub/Sub** broker.
- When User A is connected to Instance 1 and User B is connected to Instance 2, Instance 1 will publish the message to Redis.
- Instance 2 will subscribe to the Redis channel, receive the message, and push it down User B's active WebSocket connection.

### 5. Observability and Kubernetes
- Deployment using **Kubernetes (K8s)** with horizontal pod autoscalers (HPA) scaling workers based on queue lag.
- Metrics collection using **Prometheus** and log tracing via **OpenTelemetry** / **Jaeger** to track message latency from scheduling to delivery.

## Phase 2 — Scheduled Message Architecture

Phase 2 introduces a simple, correct, database-backed scheduling and execution pipeline using PostgreSQL row-level locking.

### 1. ScheduledMessage vs Message
- **`ScheduledMessage`**: Represents a future delivery job. It contains time, timezone, and execution lifecycle status values (`SCHEDULED`, `PROCESSING`, `SENT`, `CANCELLED`, `FAILED`).
- **`Message`**: Represents an actual persistent chat message delivered in a conversation thread. When a job becomes due, the worker executes it and creates a `Message` record.

### 2. Scheduler Daemon
- A separate service that polls PostgreSQL at a configurable interval (`SCHEDULER_POLL_INTERVAL_SECONDS`, default `5`).
- Query: `SELECT id FROM scheduled_messages WHERE status = 'SCHEDULED' AND scheduled_at_utc <= NOW()`.
- Handoff: The scheduler does not process deliveries itself; it makes a lightweight HTTP call to the worker service passing the due ID.

### 3. Worker Daemon & Row Locking
- The worker service runs a FastAPI web application. Upon receiving a process request:
  - Starts a database transaction.
  - Queries the message with row locking: `SELECT ... FOR UPDATE SKIP LOCKED`. If the row is already locked by another worker instance, it skips processing.
  - Transitions the status to `PROCESSING` and sets `processing_started_at`.
  - Performs an idempotency check, creates the chat `Message` record, marks the job `SENT`, records `sent_at`, and commits.
  - Triggers a REST broadcast webhook to the backend API container to publish the message over active client WebSockets.

### 4. Idempotency Strategy
- We added `scheduled_message_id` (unique, nullable foreign key) to the `messages` table.
- Before generating a `Message`, the worker queries if a record already exists with the given `scheduled_message_id`. If it does (e.g. from a prior crashed worker attempt that succeeded in inserting the message but crashed before updating the job status), the worker skips duplicate message creation and immediately marks the job `SENT`.

### 5. Timeout Recovery
- If a worker crashes while a job is in the `PROCESSING` state, the scheduler's recovery routine detects it.
- Stalled jobs (where `processing_started_at <= NOW() - SCHEDULED_MESSAGE_PROCESSING_TIMEOUT_SECONDS`) are automatically reset back to `SCHEDULED` for retry.

### 6. Timezone and DST Handling
- Naive datetime inputs are localized and validated against the selected IANA timezone name.
- Standard Python `zoneinfo` is used.
- To detect daylight saving gaps (skipped local times) and folds (ambiguous local times), we convert both fold configurations back and forth. If either fold is invalid or produces conflicting UTC instances, the system raises a `400 Bad Request` validation error.
- All scheduled times are persisted in `scheduled_at_utc` in UTC format.

### 7. Limitations & Distributed Queue
- **Database Contention**: Polling the database frequently creates continuous connection load. High message volumes will lead to query delays.
- **WebSocket Gateway Isolation**: In-memory connection maps require calling internal API endpoints on the backend node to broadcast socket messages.
- **Horizontal Scaling**: In future phases, these database tables will be decoupled into distributed messaging queues (like Kafka or RabbitMQ) and memory brokers (like Redis) to support high-throughput delivery and global connection clusters.

## Phase 3 — Distributed Queue Architecture

Phase 3 introduces a horizontally scalable, distributed queue-based scheduling and execution system using Redis as a buffer, work coordinator, and retry scheduler.

### 1. System Architecture Diagram

```
                 [ Scheduler ]
                       │
                       ▼ (SELECT due SCHEDULED)
                 [ PostgreSQL ]
                       │
                       ▼ (Atomically UPDATE to QUEUED)
                 [ Redis Queue ] (List buffer: latext:scheduled:queue)
                       │
         ┌─────────────┼─────────────┐
         ▼             ▼             ▼
     [ Worker 1 ]  [ Worker 2 ]  [ Worker 3 ] (BLPOP jobs)
         │             │             │
         └─────────────┼─────────────┘
                       ▼ (POST WebSocket Broadcast)
                   [ Backend ]
                       │
                       ▼
                  [ WebSocket ]
                       │
                       ▼
                  [ Recipient ]
```

### 2. Components & Flow

- **Authoritative Database**: PostgreSQL remains the single source of truth for users, conversations, messages, and scheduled message states (`SCHEDULED`, `QUEUED`, `PROCESSING`, `SENT`, `FAILED`). Redis only represents volatile transient work.
- **Scheduler**: Queries PostgreSQL for due `SCHEDULED` messages, transitions their status to `QUEUED` in DB, and publishes their IDs to the Redis queue (`latext:scheduled:queue`). If Redis fails, the DB transaction rolls back, preventing lost jobs.
- **Workers**: Scalable, stateless consumer instances. They pop job payloads from Redis via `blpop`. Each worker implements concurrency control via an `asyncio.Semaphore` (providing natural backpressure when busy).
- **At-Least-Once & Idempotency**: Jobs are acknowledged in Redis only after DB commit succeeds. If a worker crashes mid-execution, the redelivered job is caught by the database-level uniqueness constraint on `messages.scheduled_message_id`, avoiding duplicate message generation.
- **Retries & DLQ**: Failed jobs are scheduled in a sorted set (`latext:scheduled:retry`) with exponential backoff (0s, 10s, 30s, 90s). Exhausted retries (>= 4 attempts) are transitioned to `FAILED` in PostgreSQL and archived in the Dead-Letter Queue (`latext:scheduled:dead-letter`).
- **Observability**: Metrics are gathered via Prometheus (`/metrics` endpoints on backend, worker, and scheduler) and visualised in Grafana.

---

## Phase 2 vs Phase 3 Comparison

| Parameter | Phase 2 (DB Polling + HTTP Handoff) | Phase 3 (PostgreSQL + Redis Queue) |
| :--- | :--- | :--- |
| **Throughput** | Limited by database transactional locking capacity | Highly buffered, decoupled, scales with worker count |
| **Latency** | Low for sparse jobs; high under database locks | Low queue latency under standard worker pools |
| **Failure Modes** | Worker crashes stall messages; requires DB recovery run | Worker crashes trigger automatic queue redeliveries |
| **Scalability** | Hard to scale due to single-coordinator DB locking | Easily scaled horizontally by adding worker containers |
| **Operational Complexity** | Very Low (PostgreSQL only) | Medium (Requires Redis, Prometheus, Grafana) |
| **Database Load** | Continuous polling and locks create database overhead | Database only touched for authoritative state updates |
| **Backpressure** | None; scheduler pushes raw HTTP requests regardless | Strong; workers block-pop only when slots are available |

## Phase 5 — Distributed Real-Time Delivery

Phase 5 replaces process-local WebSocket mapping and synchronous worker HTTP handoffs with a fully decoupled event propagation model built on Redis Pub/Sub.

### 1. Unified Event Flow Diagram

```
[ Worker (Scheduled) ] ───────┐
                              ▼ (Publish message.created to Redis)
[ REST API / WS Client ] ──> [ Redis Pub/Sub ] (latext:events channel)
                              │
          ┌───────────────────┴───────────────────┐
          ▼                                       ▼
  [ Backend Node 1 ]                      [ Backend Node 2 ] (Subscribers)
          │                                       │
          ▼ (If recipient is online)              ▼ (If recipient is online)
   [ WebSocket (User A) ]                  [ WebSocket (User B) ]
```

### 2. Design and Component Breakdown

- **Decoupled Architecture**: Worker instances and backend HTTP nodes publish versioned event schemas (`message.created`, `message.status`) to a single bounded Redis channel `latext:events`. Background subscriber daemons running on every FastAPI backend instance listen to this channel.
- **Process-Local WebSocket Mapping**: Connection managers maintain user WebSocket lists locally on each instance memory map (`user_id -> List[WebSocket]`). When the subscriber daemon receives an event from Redis Pub/Sub, it inspects if the recipient is connected to the local instance:
  - If connected: delivers the payload immediately via WebSocket.
  - If not connected: ignores the event.
- **Atomic State Transitions**: To prevent duplicate status triggers, the delivery status is updated atomically in the database:
  `UPDATE messages SET status = 'DELIVERED' WHERE id = :message_id AND status = 'SENT'`
  Only the instance that actually changes the database row will emit the corresponding `DELIVERED` status event back to Redis Pub/Sub.
- **Authoritative DB & Crash Recovery**: Redis Pub/Sub is not a source of truth and does not guarantee message persistence. PostgreSQL remains the sole authority. If a client disconnects or a backend instance crashes, the client-side reconnection loop fetches the conversation history directly from PostgreSQL via HTTP REST endpoints and reconciles messages by checking unique message IDs.
- **Observability**: New Prometheus metrics are tracked:
  - `events_published_total` and `event_publish_failures_total`
  - `events_consumed_total` and `event_processing_failures_total`
  - `event_processing_duration` (Histogram)
  - `websocket_delivery_total` and `websocket_delivery_failures_total`

## Phase 6 — Kubernetes Architecture

Phase 6 introduces Kubernetes as the primary container orchestration layer for Latext, shifting the infrastructure from single-node Docker Compose into a multi-replica, load-balanced, and resilient topology.

### 1. Workload Orchestration Model
- **Namespace isolation (`latext`)**: Isolates all Latext resources.
- **Stateful workloads (PostgreSQL)**: PostgreSQL runs as a `StatefulSet` bound to a `PersistentVolume` for local data persistence. In production, this maps to managed database services.
- **Stateless workloads (Backend, Workers, Frontend)**: Backend pods run with `replicas: 2` to handle incoming API and WebSocket connections. Workers run with `replicas: 2` to consume scheduled-message queue items. Frontend runs with `replicas: 1`.
- **Scheduler Singleton**: The scheduler is explicitly deployed with `replicas: 1` to prevent duplicate claiming and scheduling of due messages.

### 2. High Availability, Probes & Graceful Shutdown
- **Liveness Probes (`/health`)**: Non-blocking static endpoint to verify process health without DB/Redis checks, avoiding cascading crash loops.
- **Readiness Probes (`/ready`)**: Verifies DB and Redis connectivity before routing traffic.
- **Graceful Shutdown Hooks**: Pods intercept `SIGTERM` signals and use a `preStop` hook to complete pending DB commits and cleanly disconnect active WebSockets.

### 3. Database connection safety budget
We enforce a database connection pool sizing constraint:
$$\text{Backend Replicas} \times 15 + \text{Worker Replicas} \times 15 + \text{Scheduler} \times 15 \le \text{PostgreSQL Safety Margin (250)}$$
This is documented and calculated dynamically during scaling tasks.
